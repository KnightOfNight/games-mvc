8. Playtest finding, fixed in-session (a73fbb0): on the operator's third
   quick waypoint teach ("remember this location as 'one-up'"), the
   model answered `Saved waypoint "one-up" at ...` WITHOUT calling
   remember (log: where_is -> end_turn, 0 receipts; store verified — no
   'one-up' row). THE MACHINERY WORKED: the false claim shipped with no
   `sudo did:` line, and the operator caught it from the missing receipt
   alone — the delivery-side layer doing exactly what #302 built it for.
   Root cause is mechanistic, not just model flakiness: ConversationStore
   replays history as plain text q/a pairs (the ruled 25.6 shape), so by
   the third teach the model's visible history showed two prior
   teach->"Saved ..." exchanges with no tool calls in sight — its own
   stripped transcript taught it that a text-only "Saved" is a complete
   response (the replay trap). Fix (bot-side only, the 25.8 precedent):
   one added standing order naming the trap — earlier turns are text
   only, the tool calls behind them invisible; a prior "Saved ..." is
   never a license to answer an action request with text alone; every
   action request requires its own tool call in the current turn. Dev
   bot restarted with the new prompt. Note: the operator's 'one-up'
   waypoint was NOT saved and needs re-teaching. A structural fix for
   the replay shape (persisting tool blocks in history, or annotating
   replayed answers) would change the ruled conversation-store design —
   design-lane if the prompt order proves insufficient.

9. Playtest finding, second variant (the poisoned history): after the
   deviation-8 restart, the operator's re-teach of 'one-up' failed AGAIN
   — this time with ZERO tool calls (log 14:57:28: straight end_turn,
   0 receipts). Mechanism: the conversation store persists across
   restarts by design, so the model's history still contained its own
   earlier false "Saved waypoint 'one-up'" claim — the lie became ground
   truth ("already saved"), self-reinforcing. The subsequent teaches
   (two-up, three-up, green-start) all landed correctly with receipts
   under the new standing order — only the poisoned name failed. The
   operator's "list all waypoints" then returned the honest store (no
   one-up), which is how the discrepancy surfaced: the receipts + honest
   queries made the poison visible. Remediation in-session: dev bot
   stopped, the dev conversation file deleted (bot-owned gitignored
   runtime state), bot restarted fresh. STRUCTURAL FINDING for design:
   the conversation store records the model's prose as the exchange
   record, but the prose can be false — the delivered exchange now
   includes machinery receipts, and persisting them with the answer (or
   otherwise marking unbacked claims) would make the replayed history
   truthful; changes the ruled 25.6 store shape, so design-lane — FILED
   as #305 (operator-directed) with three direction candidates,
   persist-receipts-with-the-answer recommended.
