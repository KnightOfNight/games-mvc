DEVIATIONS (none silent)
1. Migration dependencies: the brief's §5.1 literal lists only
   ('shyland', '0050_mcevent'); the file also carries the auth migration
   dependency ('auth', '0012_alter_user_first_name_max_length'), mirroring
   the 0034 precedent the same section says to follow exactly.
2. Live-tail cursor (75031c7): the brief's §3 notation "live from now ($)"
   is implemented as a concrete tail-id snapshot (XREVRANGE ... COUNT 1,
   '0-0' when empty), resolved inside attach handling — never XREAD $.
   Found by §7.5's live check: the $ cursor drops entries landing between
   XREAD calls, and a task-deferred snapshot misclassifies events emitted
   immediately after attach as history (the live check timed out exactly
   there). With the snapshot in attach handling, a ping/pong fence after
   attach is a hard delivery guarantee. Wire contract unchanged; the brief's
   own bare-attach + gap-empty flows are the ones exercised.
3. Stream-task failure posture (unspecified by the brief): a mid-stream
   Redis failure logs a shyland.mc warning and closes the connection (the
   agent reconnects), rather than leaving a silently dead socket. Attach-time
   failure does the same. No game path is affected either way.
4. Consumer module docstring reworded once (50c681e) so §7.2's
   grep -n 'Character' verification stays at zero hits — the hit was prose
   in my own docstring, not code.
5. LIVE_BLOCK_MS is 2000, not the brief's 5000 — found by the operator
   playtest (step 3: no events after moving). redis-py 8.1.0 (what the
   image resolves for the requirements pin redis>=5.0) changed its default
   client-side socket_timeout to 5 seconds; an XREAD whose server-side
   BLOCK equals the client-side read cap is a coin-flip race every idle
   cycle, and after ~18 idle cycles (~90s) the client lost, redis-py
   raised TimeoutError, and the failure handler closed the agent's
   socket ~3s before the operator's move records landed. A 2s block
   inside the 5s cap removes the race window entirely. Wire contract
   unchanged; no test pinned the constant. The playtest-found-fix flow
   is the workflow's step 4 (a bug against the brief's own spec: fix in
   the still-open session, redeploy dev, re-playtest).

RELATED FINDING (outside this brief, persister untouched)
The persister has the same 5s/5s race: run_mc_persister's XREADGROUP
BLOCK 5000 with the sync client's redis-py 8.1 default socket_timeout=5
produced 107 "mc persister: redis unavailable (Timeout reading from
socket); retrying" lines on the dev stack. Self-healing by design
(RedisError caught, backoff, XREADGROUP redelivers unacked — no data
loss), but each loss reconnect-churns. Applies wherever the image was
built with redis-py >= 8 (prod's 25.2 image included, quiet-hours
idle cycles). Issue callout raised in-session.
